# Smart Water Consumption Portal

A college-level MERN application for recording and reviewing water consumption across institutional buildings. Operational data comes from MongoDB; there is no fallback dataset in the React application.

For Vercel + Render + MongoDB Atlas, use [DEPLOYMENT.md](DEPLOYMENT.md). Current verification, remaining account-access steps, and changed files are recorded in [DEPLOYMENT-STATUS.md](DEPLOYMENT-STATUS.md).

## Features and stack

- React, React Router, Axios and Recharts frontend; locally bundled illustrations, icons and fonts.
- Node.js, Express, Mongoose and MongoDB backend.
- Registration, JWT login, bcrypt passwords, logout and backend role/area permissions.
- Administrators manage users, areas, daily/monthly limits, consumption, alerts and reports.
- Staff view their assigned building, limits, history, recommendations and alerts, and add consumption there.
- Daily/weekly/monthly monitoring, filtered reports, CSV download and browser printing.
- Responsive blue, white and green institutional interface with Indian number/date formatting.

## Requirements and MongoDB setup

Install Node.js 24.x (with npm), and MongoDB Community Server or provide a MongoDB connection URI. Start MongoDB before starting the application. On Windows, check the MongoDB service with Get-Service MongoDB and start it with Start-Service MongoDB from an administrator terminal if needed. On other systems, use the service command for your MongoDB installation.

The default connection is `mongodb://localhost:27017/smart_water_portal`. MongoDB Compass is optional. The database lives in MongoDB's configured data directory, separately from this source folder. The isolated automated-test databases use timestamped `smart_water_portal_test_*` names and are dropped after their tests; normal application commands use only `smart_water_portal`.

## Installation and start

Open a terminal in this project folder:

```sh
npm install
npm run setup
npm run dev
```

Open http://localhost:5173. On Windows, use npm.cmd in place of npm if PowerShell blocks npm.ps1.

Setup creates server/.env with a random JWT secret and client/.env. Development and backend start commands also run setup automatically if these files are missing. Existing configuration is preserved. One root installation installs both npm workspaces.

To start the backend and frontend separately, run these in two terminals from the root:

```sh
npm run dev -w server
npm run dev -w client
```

The backend development command exits cleanly on a port conflict, allowing the root launcher to stop the paired frontend instead of leaving it behind. Restart the command after changing backend files. Production builds require VITE_API_URL to point to an HTTPS backend. For a local build using your local backend, run `npm run build -w client -- --mode development`, then `npm run preview -w client -- --port 5173`. Normal local development uses `npm run dev`.

## Environment variables

Setup reads server/.env.example and client/.env.example. These are the source templates; actual .env files are generated locally and are not included in the submission.

| File        | Variable            | Purpose/default                                             |
| ----------- | ------------------- | ----------------------------------------------------------- |
| server/.env | MONGO_URI           | MongoDB URI, default local smart_water_portal database      |
| server/.env | JWT_SECRET          | Random secret of at least 32 characters; generated by setup |
| server/.env | PORT                | API port, default 5000                                      |
| server/.env | FRONTEND_URL        | Frontend origin; public HTTPS Vercel origin in production |
| server/.env | TRUST_PROXY_HOPS    | 0 locally; 1 behind Render's reverse proxy |
| Hosting environment | NODE_ENV | Set to production on Render; prevents local secret generation and public admin registration |
| server/.env | SEED_ADMIN_PASSWORD | Random local password used only when seeding the demo admin |
| server/.env | SEED_STAFF_PASSWORD | Random local password shared by the four seeded demo staff |
| client/.env | VITE_API_URL        | Backend origin, e.g. http://localhost:5000 locally; /api is added once |

Frontend environment variables are public. Keep database credentials and JWT secrets in server/.env only. Restart servers after changing settings. Localhost and 127.0.0.1 are both supported for the configured frontend port.

Existing local CLIENT_ORIGIN settings remain supported; FRONTEND_URL takes precedence. Production requires FRONTEND_URL explicitly, and setup never creates local .env files when NODE_ENV=production. Changing VITE_API_URL requires rebuilding/redeploying the frontend.

## Registration, login and assignment

Open Register from the login page. Enter name, email, password, matching confirmation and ADMIN or STAFF role. Passwords require at least eight characters and at most 72 UTF-8 bytes. Email addresses are normalized and unique. Registration saves the account to MongoDB, then offers a sign-in link. Both password fields have show/hide controls.

Development retains the demonstration's ADMIN registration. Production registration is STAFF-only, enforced by the backend; administrators create additional administrators in Team members. Migrate an existing administrator or seed an empty database with strong private passwords before launching production.

New staff start unassigned. An administrator assigns their building in Team members; public registration cannot grant arbitrary building access. Administrators can also create accounts directly. Staff can add records only in their active assigned area; editing/deleting consumption, user management, monitoring and reports require ADMIN. Forbidden API calls return 403 even if sent outside the UI.

JWTs expire after eight hours and are kept in tab-scoped session storage. Logout clears the token. If session restoration fails temporarily, Retry keeps the existing token; an expired or invalid token still signs out. Every authenticated API request checks the current database user and status. Password hashes are excluded from JSON responses.

## Optional database seed

For a demonstration with existing buildings and records, run this **before registering**, on an empty database:

```sh
npm run seed
```

It creates one demo administrator, four staff, seven areas, 210 varied consumption records covering the latest 30 days, and alerts calculated from actual exceeded limits. It skips insertion if any portal users, areas, consumption, alerts, or audit logs already exist; it never overwrites existing work. Seed data stays in MongoDB and is never substituted by the frontend.

The seeded administrator email is `admin@smartwater.demo`; one staff email is `rahul@smartwater.demo`. Passwords come from the private local `SEED_ADMIN_PASSWORD` and `SEED_STAFF_PASSWORD` settings; only bcrypt hashes enter MongoDB. Older local accounts may still have passwords from an earlier published demo. Change those passwords in Team members before migration. Editing seed environment variables does not change existing account passwords. Production seeds reject the earlier demo passwords and require at least 12 characters.

To intentionally replace only this application's demo collections in `smart_water_portal`, run:

```sh
npm run seed:reset
```

This clears and rebuilds `users`, `areas`, `consumptions`, `alerts`, and `auditlogs`; it does not drop the database or touch any other database. The command accepts only `smart_water_portal` or isolated timestamped portal test databases.

Reset is disabled when NODE_ENV=production. Never reset the database as part of deployment. Run the optional seed once with the API stopped; a repeat run skips existing data.

## Calculations and behaviour

- Litres only; amounts and limits must be at least 0.01. Multiple entries on the same day are added together.
- Today uses Asia/Kolkata consistently. Stored consumption dates are YYYY-MM-DD calendar strings; weeks begin Monday.
- NORMAL is below 90% of the limit. WARNING is 90% through 100%, inclusive. EXCEEDED is above 100%.
- Daily and monthly totals are checked independently. The dashboard shows the more severe status. Alerts are generated for exceeded limits; warnings appear in dashboard statuses and recommendations.
- Consumption creation/edit/deletion and limit edits recalculate alerts. One alert exists per area/type/period. Corrected totals automatically resolve alerts; another exceedance reopens automatically resolved alerts. Manually resolved alerts remain resolved to preserve the recorded review.
- Deactivating an area preserves history and blocks new entries. Deactivating a user preserves historical `recordedBy` references and blocks login. Setting responsible staff also assigns that person to the area; changing that responsibility keeps the two sides of the assignment consistent.
- Reports group by area and day. Average is total divided by recorded area-days. Violations count exceeded area-days. Report status uses daily limits; monthly limits appear on the dashboard and monthly alerts.
- Monitoring averages/minimum/maximum use recorded periods, not fabricated zero readings. Charts use the latest 30 recorded days and 12 recorded months.
- Historical records use current limits; this prototype does not version budgets. Writes are serialized inside one backend process to keep recalculations consistent. Use one backend instance.

## API summary

Public: GET /api/health, POST /api/auth/register, POST /api/auth/login.

Authenticated: GET /api/auth/me, GET /api/dashboard, GET /api/areas, GET/POST /api/consumption, GET /api/alerts. Individual resource reads enforce area scope.

Admin: user CRUD; area creation/update/deactivation; consumption update/delete; GET /api/monitoring; GET /api/reports; PATCH /api/alerts/:id/status (or PUT /api/alerts/:id).

All protected endpoints require Authorization: Bearer followed by the JWT. Queries support area, startDate/endDate, search or status where shown in the UI; monitoring also accepts Daily/Weekly/Monthly view. Errors return a success:false object with a clear message. Database outages return 503; startup fails clearly if MongoDB cannot connect.

## Tests

With MongoDB running and setup completed (keep port 5002 free for the backend restart test):

```sh
npm test
npm run build -w client -- --mode development
npm run test:e2e
```

Backend tests create and drop only their uniquely named test database. They cover registration, hashing, duplicate/invalid input, authentication, role/area restrictions, CRUD, limits, daily/monthly alerts, filters, reports, Indian date boundaries and persistence across database reconnection and backend process restart.

Browser tests require Google Chrome. The runner seeds a separate uniquely named database, starts the API on 5001 and Vite on 5174, runs Playwright, stops its processes and drops that test database. Keep those ports free. No application servers need to be started manually. Tests cover both registration roles, login/logout, user management, consumption, alerts, CSV export, charts, error/empty states and layouts at desktop, tablet and mobile widths. Generated test output goes under ignored .runtime/.

## Demonstration workflow

1. Register an administrator, or seed an empty database and log in with the seed account.
2. Create a building with a 5000 L daily and 100000 L monthly limit.
3. Record 3000 L today; review NORMAL on the dashboard.
4. Add 1500 L to see WARNING, then 1000 L to see EXCEEDED and a daily alert.
5. Resolve the alert, filter reports to the building, export CSV or print.
6. Register staff, assign the building as administrator, then log in as staff and verify their scoped history and permitted recording.
7. Restart the application; accounts and consumption remain in MongoDB.

## Troubleshooting and running on another computer

- MongoDB connection error: start MongoDB and check MONGO_URI. There is no mock fallback.
- Invalid secret: run setup or supply a random JWT_SECRET of at least 32 characters.
- API connection/CORS error: check VITE_API_URL, FRONTEND_URL (or legacy local CLIENT_ORIGIN) and the running backend.
- Port occupied: stop the older application instance or configure matching ports and origins. Vite refuses to silently change its port.
- Staff sees no data: assign their area in Team members. Inactive areas allow historical viewing only.
- Seed skipped: it protects existing data. Register an account or choose a new empty database for a fresh seeded demonstration.
- Chrome unavailable: install Chrome or change the Playwright channel to an installed browser.
- Charts load separately when needed, keeping the initial login and public-page download smaller.

Copy this source folder to another computer, install the requirements, start MongoDB, then run npm install, npm run setup and npm run dev. Register new accounts or optionally seed an empty database. Database contents are not transferred with source files. All UI images/fonts are bundled; installation requires internet access for npm packages.

The submission contains source, all three package manifests, the shared root package-lock.json, environment templates, required assets/licenses, and test source/configuration. The root lockfile covers both workspaces; separate client/server lockfiles are not needed. Use npm ci instead of npm install to reproduce the locked dependency versions exactly.

Before compressing again after local development, stop development servers and remove all node_modules folders, actual .env files, client/dist, .runtime, coverage, logs and caches from the submission copy. Keep the .env.example templates and test source files. Git ignore rules do not exclude files from a ZIP created by your file manager. No ZIP is generated by the project.
